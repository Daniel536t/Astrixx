# Architecture

## Runtime layers

1. **World model** — `src/world/types.ts` defines stable-ID entities, state, proposals, and discriminated event names. `createWorld.ts` supplies deterministic initial state.
2. **Simulation/action logic** — `WorldSimulation` advances a fixed 160 ms simulation step, owns local mutations, emits sequenced events, and provides proposal approval/rejection/cancellation. Rendering is not imported here. Confirmed external tree state can be reconciled through a monotonic guard; invalid, unverified, or older state is refused and recorded as a conflict. Local trees take two hits: `TREE_DAMAGED` (2→1, proposal stays executing) then `TREE_CHOPPED` (1→0, the felling blow that creates the log). Execution completion (EXECUTED) and outcome verification (VERIFIED) are separate: each completion site checks resulting world state before marking VERIFIED.
2b. **Settlement systems** — three task-capable workers share the world through per-worker task state (`task` on the worker, no global slots) and target-claim exclusion, so the crew fans out instead of piling onto one tree. Food consumption is deterministic (1 per worker per 600 ticks; hunger is reported, never lethal). Farms (3 wood, 2 plots) regrow on a timer and harvest like berry patches for renewable food. Houses (2 wood, 3 plots) add +2 housing over a base of 4; newcomers arrive when food ≥ 4 with room (costing 2 food), capped at 6 workers. Construction reserves materials once, supports cooperative joins, and fails honestly on insufficient wood or exhausted plots. Movement traces shed first under event-log pressure so the causal chain survives crew-scale volume.
3. **Agent decision interface** — `Agent` declares `observe()`, `decide()`, `proposeAction()`, `executeAction()`, plus optional `controlsWorker()` scoping (ManualAgent: none; ModelDrivenAgent: Moss only; default: all). Observations carry per-worker focus, the full worker roster, claimed targets, and farm readiness. `LocalGathererAgent` implements deterministic nearest-resource policy with claim exclusion and farm awareness. `ModelDrivenAgent` keeps the same interface but sources each turn's decision from an injected `DecisionProvider` (live NIM, TrueForge-routed, or scripted mock); its pending decision persists across the turn's steps so the worker is not idled mid-turn. Human pause/resume interrupts simulation; `stop()` prevents further turns and `cancelProposal()` recalls pending (not executing) proposals.
4. **Governance** — proposals, risk levels, and explicit human approval/rejection are kept distinct from transaction signing/submission. Only `LOW` risk is auto-approved locally. Higher-risk proposals remain pending until an explicit approval; never infer a transaction signer from permission alone.
5. **Event log** — typed `WorldEvent` records carry monotonic event IDs/sequence numbers, simulation tick, entity ID, and structured data. The bounded in-memory tail is 240 records. Chain stage names distinguish local state from real RPC receipts; local mode never emits fabricated confirmations or verified-chain state.
6. **Rendering/presentation** — `WorldRenderer` maps authoritative IDs and local world state to Three.js groups. `GlbNatureAssetCatalog` asynchronously loads bundled CC0 tree/stump GLBs with procedural fallbacks; terrain, ground cover, worker, cabin, berries, basket, and log presentation remain procedural. Meshes never store game state. Tree chop progress is driven exclusively by simulation state.
7. **UI/observatory** — a lightweight DOM UI shows resource stockpiles, agent activity, causal chains, human pause, and event stream. It explicitly labels the current mode `LOCAL SIMULATION` / `LOCAL · NOT ONCHAIN`.
8. **MagicBlock/Solana** — `WorldStateAdapter` separates local simulation from chain operations. `LocalWorldStateAdapter` labels itself `local-mock` and rejects network operations. `MagicBlockDevnetAdapter` implements one owner-signed tree PDA initialize/delegate/chop/read/commit slice; a high-risk tree proposal blocks local chopping until confirmed reconciliation. It refuses use unless the Devnet program is executable, requires a human wallet, checks RPC signatures/account data and records confirmed stages. Source and adapter are not deployed or chain-verified; consult [MagicBlock status](MAGICBLOCK.md). Offline program/client interface pins (program id, PDA seeds, 68-byte TreeState layout, local/chain felling-blow alignment) live in `src/magicblock/ProgramInterface.test.ts`; live-devnet tests are gated behind `ASTRIX_LIVE_DEVNET=1`.
9. **Model runtime (server-side)** — NVIDIA NIM candidates are registered in `src/agent/nvidia/ModelRegistry.ts` (credential slots A/B, never merged). `NimClient` makes non-streaming completions; keys come from `NVIDIA_NIM_API_KEY_A/B` environment variables and never reach the browser. Gemini and OpenRouter sit behind the replaceable `InferenceProvider` interface (`src/agent/providers/`): `GEMINI_API_KEY` / `OPENROUTER_API_KEY` select via `ASTRIX_AI_PROVIDER` / `ASTRIX_AI_MODEL`, with explicit opt-in fallback only (`ASTRIX_AI_FALLBACK`). TrueForge (`src/agent/trueforge/TrueForgeRuntime.ts`) is the agent runtime: local server at `TRUEFORGE_BASE_URL` with per-slot `custom` providers (`nvidia-nim-a/b`), a saved `astrix-steward` agent with a JSON-schema decision contract, session-scoped turns, and cancellation. The agent backend (`server/agent-server.ts`, `npm run agent:server`) runs headless model loops and labels every response `trueforge` or `direct-nim`; it also serves `/api/interpret` (command → validated goal) and `/api/decide` (observation → labelled decision text) for the browser game. ASTrix MCP tools (`src/mcp/astrixTools.ts`, `server/mcp-server.ts`) expose read-only observation plus proposal creation only — no approval or execution authority. Model reasoning traces are never logged or displayed; only intents, expectations, and recorded outcomes are.
10. **Game layer (`src/game/`)** — player commands become explicit `GameGoal`s via a deterministic parser (model interpretation only for unrecognized input, schema-validated). The reactive `planner` derives each next step from fresh observations (no fixed scripts). `ControlMode` (direct/delegated/supervised) sets the approval threshold (`LOW`/`MEDIUM`/`LOW`) and whether the model loop is consulted; the browser falls back to the labelled planner when inference is slow or down. `GoalRunner` drives headless goal runs with per-turn evidence rows and one-shot rejection replanning. Construction (`BUILD`, always HIGH, 2 wood → house with staged visuals) and ambient villagers extend the sim without touching the wood/food loops. Bridges are honestly unsupported: the world has no river or gap, and the parser says so with a house alternative.

## Causal flows

- **Wood (local demo):** `standing tree → observe/decide → target + LOW-risk proposal → worker moves → chopping → tree health/depleted reflects simulation → stump/log created → pickup → carrying → delivery → settlement wood increments`. Felled stumps can be replanted (`PLANT`, LOW-risk): sapling → standing timber on its own over `SAPLING_GROW_DURATION`.
- **Houses:** 3 fixed plots spread around the settlement (east, west, north) so built houses never intersect the cabin; each renders a construction frame then a finished body (walls, roof, chimney, window, door).
- **Food (local demo):** `available berry patch → observe/decide → target + LOW-risk proposal → worker moves → harvest → patch visibly harvested → basket created → pickup → carrying → delivery → settlement food increments`.
- **Farm (renewable):** `built farm → growing progress → ready (golden crops) → HARVEST → food → farm back to growing`. Consumption drains the stockpile per worker over time; hunger/low-food are events, not deaths.
- **Housing/growth:** `2 wood → HIGH-risk BUILD → approval → staged construction → complete house (+2 capacity) → newcomer at food ≥ 4 (−2 food)`.
- **MagicBlock tree slice (source implemented, not deployed):** human-approved high-risk proposal → explicit wallet authorization → ER chop submission/confirmation → decoded account/nonce verification → local state reconciliation (no local log fabrication). Delegation and base commit/undelegation are separately verified. No live chain operation has been run.

Low-risk resource gathering is auto-approved in local mode. High-risk proposals stay `PROPOSED` until explicit approval or rejection. Real transaction authority/session keys must be temporary and instruction-scoped, and only a user-controlled wallet may create/revoke them. Read [MagicBlock plan](MAGICBLOCK.md) for prerequisites and failure semantics.

Simulation is deterministic for the same ordered fixed-step calls. Simulation ticks, not wall-clock time, timestamp local events. Procedural environment and animation are presentation only; animation completion never decides a chop, harvest, or delivery.

## Architecture checklist (open)

- **Proposal lifecycle completeness.** Every proposal must reach a terminal state (`VERIFIED`/`FAILED`/`REJECTED`/`CANCELLED`); no path may strand one as `PROPOSED`/`APPROVED`/`EXECUTING` forever. Audited so far: stale harvest tasks fail their authorizing proposal (shared already-`VERIFIED` proposals are never clobbered); stale chop tasks clear without terminating a legacy `GATHER` proposal (same leak class, still open). The approvals UI lists only `PROPOSED` entries, so stranded non-proposed proposals are invisible — lifecycle evidence must not depend on that list.
- **Bounded history.** The event tail (240, movement shed first) and decision journal (40) are capped. `proposals`, `plans`, and `speculative` records are currently uncapped; any cap/eviction must preserve a truthful account of completed, rejected, failed, cancelled, and blocked work.
- **E2E predicate discipline.** Browser stage predicates assert world/activity-level outcomes (any eligible worker); worker-identity requirements belong in unit tests. Scenarios that depend on live chain state (delegated farm) assert conditionally on the reconciled state, never on a fixed chain expectation, and never reset chain state to satisfy the test.

## Run/test

`npm run dev`; `npm run typecheck`; `npm test`; `npm run build`; `npm audit --omit=dev`. With Vite running, `npm run verify:phase3` captures desktop/tablet scene stages and verifies both local loops, camera controls, pause behavior, loaded licensed GLBs, and browser console output. Browser results are local simulation evidence only, not chain tests.
